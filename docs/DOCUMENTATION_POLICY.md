# Правило документирования ключевых внедрений

Принято пользователем 8 ноября 2026. Постоянное правило проекта AltaiR EQ; текст также пригоден для передачи в основной чат Mix Studio.

- Каждое ключевое внедрение сопровождать Markdown-документацией в том же изменении: DSP, параметры, UI с новым поведением, состояние, автоматизация, интеграция, сборка или выпуск.
- Использовать docs/changes/YYYY-MM-DD-short-name.md либо дополнять подходящий существующий документ. Мелкие косметические исправления можно объединять в одну запись; не создавать бюрократический отчёт на каждую строку.
- Указывать дату, статус, назначение, затронутые файлы/компоненты, принятое решение и существенные альтернативы, проверки с фактическими результатами, ограничения и следующий шаг. Для несовместимых изменений описывать миграцию и откат.
- Разделять предложено, реализовано и проверено. Не выдумывать измерения, качество звука, пройденные тесты или совместимость.
- Обновлять SPEC/ARCHITECTURE/STATE_FORMAT и CHANGELOG, когда меняется соответствующий контракт. Избегать противоречащих друг другу копий.
- Документацию вести рядом с исходниками. Экспорт для чтения не заменяет проектные инструкции и историю изменений.
- В итоговом сообщении давать ссылку на запись и кратко сообщать фактически выполненную проверку. Не объявлять ключевое внедрение завершённым без этой записи.
